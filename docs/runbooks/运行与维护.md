# 运行与维护

本文说明现有服务器的运行方式和已知恢复边界。环境安装、测试和构建命令以 [快速开始](../../README.md) 为准；操作权限遵循 [AGENTS.md](../../AGENTS.md)。

## 服务与运行配置

现有部署位置是 `10.99.8.16:/home/bgpdata/domeye-new`。前后端由 systemd 管理，服务定义实际位于服务器：

| 对象 | 配置或入口 |
|---|---|
| 后端服务 | `/etc/systemd/system/domeye-new-backend.service`，执行本项目 `scripts/backend.sh` |
| 前端服务 | `/etc/systemd/system/domeye-new-frontend.service`，执行本项目 `scripts/frontend.sh` |
| 后端运行配置 | `/home/bgpdata/domeye-new-runtime/backend.env`，项目外普通文件，权限必须为 `0600` |
| 启动日志 | systemd journal |
| 后端应用日志 | 由 `DOMEYE_LOG_DIR` 指定；启动器默认使用运行配置所在目录下的 `logs` |

安装的 unit 是当前生效配置的核对入口；运行目录下 `systemd/` 的安装副本不代表实时生效状态。这些文件尚未作为服务定义纳入本项目 Git。

该常驻方式仍运行 Vite 开发服务器和 Flask 的现有启动入口。它不自动托管 `frontend/dist`，也没有在本项目建立正式静态站点/WSGI 发布与版本回滚流程。前端构建完成后不会自动切换运行版本。

端口默认是前端 `127.0.0.1:28471`、后端 `127.0.0.1:28473`。前端代理 `/api/v1` 和 `/api/v2`。前端脚本支持 `DOMEYE_WEB_HOST`、`DOMEYE_WEB_PORT`、`DOMEYE_API_TARGET` 和 `DOMEYE_NODE_BIN`；调整前须同时核对生效 unit、后端监听和访问隧道。

后端配置通过 `DOMEYE_RUNTIME_ENV` 定位，启动器只接受 [允许的键](../../scripts/run_backend.py)，不执行配置内容。配置包括数据库连接、INFO 静态信息、国家中断读取制品及可选 P0 发布目录。凭据不写入文档、命令输出或 Git；迁移时取得该项目获准使用的独立配置。启动器的环境和只读事务保证见 [系统结构](../architecture/系统结构与数据流.md)。

## 查看与管理常驻服务

以下命令在服务器执行。先查询实时状态，不将文档中的运行方式当作服务在线证明：

```bash
systemctl show domeye-new-backend.service domeye-new-frontend.service \
  -p Id -p ActiveState -p SubState -p UnitFileState -p NRestarts -p FragmentPath
```

现有 unit 使用 `Restart=on-failure`，异常后间隔 5 秒重试，60 秒内最多启动 5 次；这不是无限重试。检查 `UnitFileState` 确认是否开机自启，检查 `ActiveState` 和实际访问确认是否运行。

按当前任务选择一个操作，不需要依次执行所有操作：

| 操作 | 命令 |
|---|---|
| 启动已安装服务 | `systemctl start domeye-new-backend.service domeye-new-frontend.service` |
| 重启服务 | `systemctl restart domeye-new-backend.service domeye-new-frontend.service` |
| 停止服务 | `systemctl stop domeye-new-frontend.service domeye-new-backend.service` |
| 为已安装服务启用开机自启 | `systemctl enable domeye-new-backend.service domeye-new-frontend.service` |
| 读取近期日志 | `journalctl -u domeye-new-backend.service -u domeye-new-frontend.service -n 80 --no-pager` |

前台调试前停止对应常驻服务，再执行 README 中的前台命令。调试结束后退出前台进程，用上表启动命令交回 systemd。只修改运行配置文件时需重启后端；只有修改 unit 定义后才需要先执行 `systemctl daemon-reload`。

## 从本机访问

在客户端建立隧道并保持该命令运行：

```bash
ssh -N -L 127.0.0.1:28471:127.0.0.1:28471 root@10.99.8.16
```

随后打开 [Domeye 页面](http://127.0.0.1:28471/)。若本机该端口已有本项目隧道，可复用现有连接；先识别占用者，不终止不相关进程。

SSH 隧道属于客户端访问通道。客户端断开或重启后可能需要重新建立；服务器服务开机自启不意味着客户端隧道自启。

## 启动后检查

在服务器上检查后端健康、前端资源和代理：

```bash
curl --fail --silent --show-error --max-time 15 http://127.0.0.1:28473/api/v1/healthz
```

```bash
curl --fail --silent --show-error --max-time 15 -o /dev/null -w '%{http_code}\n' http://127.0.0.1:28471/
```

```bash
curl --fail --silent --show-error --max-time 15 http://127.0.0.1:28471/api/v1/healthz
```

健康接口不要求数据库或业务制品可用；三个检查分别证明对应的 HTTP 层。实际事件、指标和浏览器交互需要单独的业务验证，不能由这些结果推定。

## 排障与恢复边界

| 现象 | 检查与处置 |
|---|---|
| 端口占用或前端严格端口检查失败 | 核对对应服务和监听进程；避免前台与 systemd 重复启动，不直接终止其他项目服务 |
| 缺少 Python 或前端依赖 | 核对本项目依赖目录；按 README 的安装流程恢复，前端 Node 选择逻辑以启动脚本为准 |
| 后端运行配置被拒绝 | 核对项目外普通文件、权限和允许键；不要直接打印含凭据的完整文件 |
| 服务持续失败并达到启动限制 | 先读取日志并修复原因，再使用 `systemctl reset-failed <对应服务名>` 和 `systemctl start <对应服务名>` |
| API 在线但 P0 首页不可用 | 检查是否配置了有效 P0 制品及返回的准入状态；状态含义见 CONTEXT，启动服务不会重建这些制品 |
| 国家中断返回不可用或发布不匹配 | 核对请求的发布身份、实际选择的制品及其完整性；来源选择规则见架构文档 |
| 远端可访问、本机打不开 | 核对客户端隧道、本机端口和远端目标；无需因此重启正常的后端 |

恢复现有运行环境时，先核对项目路径、生效 unit、独立运行配置及所引用的数据目录，再恢复本项目依赖，最后启动服务并进行上述检查。路径或配置变更后重新核对服务实际使用的位置。

数据制品丢失、数据库需重建、原机不可用时的完整恢复流程为 **Unknown**。本仓库没有提供对应生产管线、备份验收或正式版本回滚流程；不得将“重新启动进程”记录为“数据已恢复”。问题和后续验证结果按 [文档路由](../../README.md) 分别进入 Issue 与交接记录。
