# 采用 DuckLake、Parquet 与 PostgreSQL 分层存储

为新 RIB／UPDATE 数据统一支撑资源统计、动态特征、六类异常及详情、国家增强分析，决定使用 Parquet 保存历史数据主体、DuckLake 管理数据集、PostgreSQL 保存目录与运行状态及业务查询副本、DuckDB 执行历史分析。该选择使历史输入和中间结果能够跨计算复用，新增计算可以独立补算与发布，同时保留运行状态的事务恢复能力。

**状态：存储决策已接受，部分候选实现已有验证；完整业务性能、恢复与交付仍未验收。** 2026-09-13 的初版只确定存储方案。后续原生 M2、直接批次和文件级计算检查点已分别实施，2026-09-18 又简化了计算侧路径字典与规范态保存；不能继续把全部内容写成“未接入”，也不能因此宣称真实业务链已经可用。首版按单机处理设计，数据文件位于 Git 外的专用持久磁盘目录；代码、配置和真实数据的边界沿用 [AGENTS.md](../../AGENTS.md)。当前实现以[系统结构与数据流](../architecture/系统结构与数据流.md)为准，分版本测量及限制见[加速改动汇总](../architecture/数据流水线加速改动与当前困境.md)。

**2026-09-13 实施顺序调整（已接受待实现）：** 用户要求完整保留旧 DomeyeCore 的逻辑、状态和数据，结合 DomeyeNew 跑通一天全链路。下一次全天全量前，先修复解析错误，加入解析／观察入库的完整输入文件级 checkpoint，并通过强制进程中断恢复与连续运行一致性验收。完成一日全链路后，再替换现有前端底座、验证新增计算，最后完善复杂业务状态、活动事件及跨存储补偿等完整恢复协议。首轮仍采用独立候选运行，只有完成全部核验后才业务发布；文件级 checkpoint 不等于整批发布，也不表示下文完整协议已实现。具体顺序、恢复资格与验收范围见[新架构一日全链路迁移计划](../architecture/新架构一日全链路迁移计划.md)。

## 统一解析通路（2026-09-15 已接受，待完成迁移）

逻辑数据依赖为：RIPE RIS／RouteViews → 原始 MRT → libbgpdump → 结构化 Observation → 路由状态与业务计算 → 后续分析。它不要求先把完整 Observation 入湖再开始计算。直接主通路由同一有序批次同时驱动归档与内存计算，DuckLake 保留历史观察和核验依据；RCA 不进入逐条热循环。原始 MRT 永久保留为原始证据，Observation 带来源、原始位置和解码版本；路由状态与异常结论仍受[底层证据 ADR](0001-routing-observation-evidence-boundaries.md)的观察范围和未知值约束。RouteViews 等尚未验收的输入不因该逻辑图自动取得准入资格。

采用 libbgpdump 作为统一底层解析器，解码文本以固定版本 bgpdump 为准，不为逐一复现旧 Python parser 的字符串表现增加生产转换。保留原始属性、AS_SET／AS4_PATH、时间精度及来源顺序；项目的归属与路由状态规则独立于文本格式。新旧结果比较区分证据或语义差异与纯文本差异，前者必须核对，后者按解码版本记录。`prefix` 作为规范网络键时屏蔽无意义填充位，`raw_prefix` 保留线上原字节；这属于 BGP 语义，不能用显示字符串替代网络身份。

**契约迁移原则（2026-09-15 用户确认）：** 旧解析器可以替换；M2 数据契约原则上保持稳定。如果契约丢失必要的 BGP 语义，必须明确缺项、升级契约版本，并说明旧数据迁移和消费者适配，不让 libbgpdump 模仿旧解析错误。现有字段可准确表达的适配错误直接修正，不为维持错误输出而固化版本。AS4 重建属于路径解释差异，不能笼统归为格式差异：原 AS_PATH／AS4_PATH 与 ASN 宽度继续分别保存，`as_path_text` 绑定解码版本并允许记录 bgpdump 的重建结果；`raw_origin_asn` 与项目归属结果仍分别表达原证据和当前规则，不因显示文本补成已归属。

新链路正确性验证完成后，旧 Python parser 逐步退出生产数据通路，最多保留为测试／回归工具。首份 RRC25 RIB 已完成独立候选；后续按用户授权将原生入口接入现有多文件 M2，补齐 UPDATE 并验证固定真实日。`route-pipeline` 候选入口已接直接批次通路；默认全日迁移驱动、RouteViews、真实日下游计算与生产切换仍须分别验收。资源与资格边界见[原生候选运行说明](../runbooks/运行与维护.md#首份-rib-原生-m2-候选)。

## 数据归属与权威来源

| 数据 | 存储位置 | 保存与消费原则 |
| --- | --- | --- |
| 原始 RIB／UPDATE、外部参考资料 | 原始文件目录 | 保留原件、来源、时间范围和校验和；登记后不覆盖原件 |
| 规范化路由观察、原始 Peer 属性、路径字典、会话与缺口证据 | DuckLake 管理的 Parquet | 按来源和时间批量追加，保留原始位置、精度、顺序及未知值；派生身份与原始属性分开 |
| 历史路由状态 | DuckLake 管理的 Parquet | 周期性完整基线加有序状态变化；完整仅指声明的观察范围，不代表全网或连续性已获证明 |
| Resource／Feature 历史结果 | DuckLake 管理的 Parquet | 按模块、算法版本和时间范围保存，口径及单位随版本绑定 |
| 六类异常生命周期、详情及国家增强分析明细 | DuckLake 管理的 Parquet | 保存事件修订、固定观察集合、时间序列和路径证据，供复用和追溯 |
| 当前路由、窗口累计、活动异常等工作状态 | 计算进程内存；PostgreSQL 保存恢复检查点 | 直接主循环共用规范路由及路径，保留业务确需的不同索引；完整文件末批量持久化，并共同确认该链路的状态、结果引用和游标。独立补算使用独立状态空间 |
| 页面摘要、事件检索、常用统计 | PostgreSQL | 从已交付并核验的历史结果构建查询副本，经业务发布后供页面读取，可从上游重建 |
| 输入登记、任务进度、质量结果、业务发布记录 | PostgreSQL | 使用事务管理，区分执行身份、数据身份和业务发布身份 |

PostgreSQL 中有两类目录职责。DuckLake 自行管理表结构、文件清单、统计信息和存储快照；Domeye 管理输入清单、算法及规则版本、观察范围、质量、交付和业务发布记录。Domeye 引用 DuckLake 的表和快照，不另建一套历史 Parquet 文件目录与其同步。原始文件与尚未交付的暂存文件仍由 Domeye 登记。

DuckLake 的规范采用 SQL 目录数据库与 Parquet 文件，官方支持以 PostgreSQL 作为目录数据库；该能力是选型依据，不是本项目性能结论。[DuckLake 规范](https://ducklake.select/docs/stable/specification/introduction)、[目录数据库选择](https://ducklake.select/docs/stable/duckdb/usage/choosing_a_catalog_database)

已有规范化 SQLite 制品继续作为兼容读取或上游输入，不改写其内容和身份。新统一历史层采用本方案；是否、何时转换既有制品属于后续迁移工作，不把新副本和旧制品混称为同一个权威版本。

## 新增计算与版本规则

新增计算采用独立模块和独立数据集，登记输入依赖、输出结构、算法与配置版本、计算范围及完成进度。持续累计的计算另有自己的 PostgreSQL 工作状态；历史补算使用独立运行身份和状态空间，不修改正在运行的状态。

例如新增国家中断恢复速度，优先复用已有可见性结果，或充分的路由基线与变化记录；不足时重放规范化观察，只有必需字段未保留时才重新解析 MRT。补算范围包含指标所需的基线或预热历史，不能因为只查询一个窗口就假定窗口之前的数据无关。上游本身缺少证据时保留 Unknown。

每个数据集分别记录结构版本、算法及规则版本、输入版本和业务发布引用。新指标通常建立独立数据集；同一数据集增加字段可使用 DuckLake 的结构演进，但结构演进不会计算旧数据缺失的指标，不能将默认零值当作历史结果。[DuckLake 结构演进](https://ducklake.select/docs/stable/duckdb/usage/schema_evolution)

路由对象、观察顺序、未知起源、会话缺口及状态解释遵循[路由观测证据 ADR](0001-routing-observation-evidence-boundaries.md)，不因更换存储而放宽。路径字典允许复用相同属性值；不同原始观察不能按内容去重。输入或解释规则变化产生新的可追溯结果版本，不能静默覆盖已被引用的结果。

一次国家分析通过 `publication_id` 固定各数据集版本、外部参考资料和固定观察集合。DuckLake 存储快照、BGP 时点路由状态和业务发布版本分别表达；页面不能拼接各表的任意最新值。领域术语以 [CONTEXT.md](../../CONTEXT.md)为准。

## 计算与查询方式

- 共用路由重建计算，Resource、Feature、Detection 根据需要消费规范化观察或路由变化。下游若需要某时点状态，须使用对应输入游标和版本，不能读取已经向前推进的当前表替代历史状态。
- 工作状态在内存中逐条增量更新，直接计算业务字段，结果有界批量写出。2026-09-18 的直接候选取消计算侧路径 SQLite 往返和计算中规范态落库；完整文件 EOF 及归档检查点成立后，再按有界块保存规范态和业务变化。保留解析器恢复索引与校验，不等于所有 SQLite 或存储步骤都可删除。
- `prefix_dict` 是唯一规范路由负载，路径正文共享；业务索引的 VP、AS_SET、起源等不同语义仍须保留。编号索引与去重文本随输入增长，不能把有界展开缓存等同于整个工作集有界。
- 一个文件内同一对象多次变化可合并为最终持久化值，但业务逐条读取紧邻的必要旧值并计算，不能先推进整批最终态再检测。重复宣告仍影响 Feature；原始观察不能被最终状态或变化键替代。
- 历史结果批量写入 Parquet，主要按时间和 Collector 组织，控制小文件数量；排序、文件及行组大小根据查询负载确定。新增指标不默认复制全部上游数据。
- 当前直接候选按完整文件确认：RIB 保存一次基线，UPDATE 保存变化。尚未采用“每 10 份 UPDATE 才保存”或周期性全量快照。检查点同时包含窗口、活动事件及恢复必需状态；BGP 路由基线不能替代其他计算模块的检查点。
- DuckDB 执行历史扫描、关联和聚合；常用结果进入 PostgreSQL 查询副本。生产与补算仍由显式离线入口执行，Web 只读消费已发布数据。

上述为已接受的主线和当前候选实现约束。可重建路径索引不再单独强同步保存，代价是内存容量及恢复重建成本必须实测；文件末保存减少中途等待，不能保证总保存时间同样下降。机制、真实组件及完整试跑结果分别见[加速改动汇总](../architecture/数据流水线加速改动与当前困境.md)。完整 RIB＋8 小时的一小时门槛未通过；当前版本完整耗时和容量仍为 Unknown，已知检测集合枚举恢复问题尚未解决。

## 后续完整恢复协议目标（基础文件级恢复提前实施）

本节保留下列完整目标协议。第 1、2 步的路由、窗口、活动事件和文件游标恢复已进入当前候选范围，必须验证恢复后的继续计算；第 3、4 步的跨存储交付、查询副本、业务发布与重试补偿仍属后续验收。早期实施顺序保留于[迁移计划](../architecture/新架构一日全链路迁移计划.md)，当前次序以本 ADR 顶部修订为准；基础文件级恢复通过不能代替完整协议验收。

采用“状态事务加可重试结果交付”。PostgreSQL 普通工作表与 DuckLake 输出不假定处于同一事务，即使 DuckLake 目录也存放在 PostgreSQL 中。

**部分实施（2026-09-16）：** 有序批次直接消费候选将下述第 1、2 步扩展到规范路由、既有 Feature 窗口计数和 Detection 活动事件，在完整文件边界提交恢复状态、消费位置和已核验的不可变结果引用。实际实现与人工验证范围以[系统结构](../architecture/系统结构与数据流.md#文件级路由状态流水线隔离候选)为准。第 3、4 步的结果交付、查询副本和业务发布尚未由此入口实现；候选文件恢复不等于完整协议或真实业务验收。

**2026-09-18 边界说明：** 下列协议中的“批”在当前直接计算候选中是完整输入文件，不是每个 Arrow 段。业务变化保存使用 `business-state/v2`，最新内部运行绑定为 `route-batch-pipeline/v3`；不同版本不能原地续跑。状态正文恢复一致还不足以证明后续业务一致，活动事件及旧检测集合选择的继续计算验收仍是缺口。

1. 本批计算完成后，将输出写入不可变暂存文件，完成持久化、完整性校验和清单封存。暂存文件与数据文件一样位于可靠的 Git 外存储，不能只依赖进程内缓冲或可随时清理的临时目录。
2. 在一个 PostgreSQL 事务中提交本模块的工作状态变化、输入游标和待交付文件记录。事务确认回滚时，丢弃未提交的内存状态；提交响应不明时，先核对持久化的批次记录和游标，再决定恢复位置，不得单独推进进度。此时输出仍未向业务消费者发布。
3. 发布程序核对待交付记录，将结果及批次完成回执放入同一 DuckLake 事务提交。固定批次身份绑定模块与规则版本、输入版本和处理范围，重试复用身份；单写入者及回执核对共同防止重复交付，同身份出现不同内容时拒绝继续。
4. DuckLake 提交成功后记录交付状态及输出版本；业务所需结果、查询副本与质量检查全部就绪后，才在 PostgreSQL 中提交业务发布记录。页面固定读取该发布绑定的数据集与查询副本版本。

每个计算分区保持单写入者。模块可拥有不同进度；下游只消费已交付且明确绑定版本与游标的输入，待交付记录数量和暂存空间均须有资源上限，达到上限时暂停推进。

| 中断位置 | 恢复预期 |
| --- | --- |
| 暂存文件封存后、PostgreSQL 状态事务提交前 | 保留旧状态和游标；未被事务引用的文件不能作为已完成结果 |
| PostgreSQL 提交响应丢失、结果未知 | 核对同批次的状态版本、游标和待交付记录，确认提交结果后恢复，不能仅凭异常就重放累计 |
| PostgreSQL 提交后、DuckLake 提交前 | 从已提交工作状态恢复，继续交付对应文件；不重复累计已完成输入 |
| DuckLake 提交成功，但确认响应丢失或 PostgreSQL 交付状态未更新 | 查询同批次完成回执并核对内容，复用输出，补记交付状态；不能直接再次追加 |
| 数据已交付，但业务发布或查询副本未完成 | 保留旧业务发布；完成剩余步骤后再发布，不提前对外宣称可用 |

DuckLake 提供事务和快照隔离，用于保证其内部数据与完成回执一致；跨存储的恢复预期仍需由上述协议实现并验证。[DuckLake 事务](https://ducklake.select/docs/stable/duckdb/advanced_features/transactions)

暂存文件在交付完成前保留。清理历史文件、快照或检查点前，核对有效发布、运行中读取和恢复依赖；被引用的数据不能提前删除。备份必须同时覆盖 PostgreSQL、DuckLake 引用的数据文件、原始文件及恢复必需的待交付文件，并能恢复相互匹配的版本。校验和不能替代备份，普通进程中断恢复也不自动证明断电或磁盘损坏恢复能力。

## 取舍与代价

| 考虑过的方式 | 本次选择理由 |
| --- | --- |
| 所有历史明细和新增中间结果都放入 PostgreSQL | 未选择。历史回填、索引和大量明细写入会集中在数据库；本次将历史扫描与工作状态更新分开，保留 PostgreSQL 的事务状态和快速查询用途 |
| Parquet 加自有文件目录协议 | 未作为新统一历史层采用。批量制品可以使用简单目录，但本次已需要结构演进、快照、交付和版本管理，选择复用现成数据集管理能力 |
| Iceberg 管理历史表 | 未选择。它也支持原子快照更新；本次单机、DuckDB 与 PostgreSQL 的组合直接采用 DuckLake 的 SQL 目录模型。跨引擎生态不是此次决定因素，未据此断言两者性能高低 |
| DuckLake 加 Parquet，并保留 PostgreSQL 工作状态及查询副本 | 采用。新增分析结果独立演进，历史数据可复用；代价是必须维护跨存储交付、版本引用、查询副本及配套备份 |

Iceberg 的原子表快照能力见[官方一致性说明](https://iceberg.apache.org/docs/latest/reliability/)。采用 DuckLake 不消除历史补算成本，也不证明它在 Domeye 负载下更快；优势预期来自数据分工、批量处理与可复用上游，需用实测核对。

## 待实施与验证

实施先后以本 ADR 顶部的后续主线调整为准：当前候选须先验证路由、窗口、活动事件的恢复后继续计算一致性，再进行正式完整性能验收；跨存储交付、新增计算和生产切换另行验收。下列项目仍有待完成部分，不表示已有组件全部未实现，也不表示所有恢复目标已经完成。

- 锁定 DuckLake、DuckDB、PostgreSQL 及相关扩展的兼容版本，确定机器合同、模块状态结构与迁移方式。
- 用完整 RIB／UPDATE 验证规范化写入、路由计算、状态持久化及结果读取的吞吐、内存和磁盘上限；已有历史 M2、组件及失败试跑数据不能当作最新全链路数值。补算、页面查询收益和新版完整链路耗时仍为 Unknown。
- 验证连续运行与各提交边界中断后恢复的逻辑结果一致，包括窗口计数、活动异常、事件生命周期、详情和重复交付；人工文件候选验证与真实数据、跨存储交付、生产验收分别记录，不能互相代替。
- 验证新增一种国家分析中间结果能够独立补算与发布，且不修改既有结果、不污染正在运行的工作状态。
- 验证文件与目录的配套备份恢复、版本保留和安全清理；现有 SQLite 迁移、页面接入和全站数据覆盖另按已授权任务实施。

本 ADR 补充存储决策，不替代底层证据 ADR 中尚未解决的 Peer／Session 关联、RIB 与 UPDATE 切点对齐等问题。存储选型通过不表示连续重建或六类异常已可用。已停止的 RRC25 试点继续按既有执行回执和[数据台账](../data-assets-and-admission.md)说明状态；本次文档化不接管、重启或重新登记该任务。
